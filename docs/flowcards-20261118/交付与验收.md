- ZIP核对：内含旧版01—05，04回传模板和05现场规则已读取；没有新版06/07整模双版附件。以单独新版主文档为准，不因ZIP缺件漏做整模。
- 当前线上SHA：**无法确认**。本轮只读SSH公钥连接返回认证失败，没有尝试密码、没有写服务器。11/16历史交付不能代替今天部署核实。
- 工作区未找到`AGENTS.md`。本轮阅读了相关模型、服务、迁移、测试、提交差异与现有业务交付记录；没有声称可访问全部原始历史会话。
- 本机9/21旧数据库不是当前正式库；本轮未把它当真实样本。所有写入验证均为新建隔离SQLite及合成样本，**无正式测试出退货、无历史回填**。

最重要的边界：预印模数不记产量；内部卡不是客户流程卡；来源订单不替代实际交付分摊；照片不代表完成；定点不自动扣孔；补打不新建实物包；没有证据不补造历史。

## 4. 新关系、快照与不变量

```text
稳定产品ID + 明确订单项次集合 + 可空原生产任务
                  ↓
          准备组 → 明确生成 → 内部卡(一包一ID)
          标准/外观/需整模/实际模具图/孔数口径/模板快照
                  ├─ 一份工序事实 → 明确覆盖一张或多张卡
                  ├─ 原始照片 → 只证明归档，不自动完成
                  └─ 出货来源关系 → 稳定出货Batch
                                      ├─ 原物理行/实际履约分摊
                                      └─ 原退回 → 原再出货 → 下一轮
```

三种关系分开：**生产来源/计划订单**、**客户流程卡及实物包**、**实际交付分摊**。新卡不向原数量服务提交任何数量。

- 卡组保存产品和订单显示快照、标准原文来源及版本、外观ID/名称/顺序、整模选择依据、实际模具和图版本、有效/已确认总孔数、计划范围、模板与纸张尺寸。
- 独立卡保存原日期、计划模数、固定分母。`2050/100→21张，末张50M`；追加组不会把原`3/20`改为`3/24`。
- 准备组可以留痕修订、补齐模数和来源；生成后拒绝改快照。共同实测保存一条事实及覆盖关系，不复制多份作业量。
- 实测、未测、不适用、未知和真实0分开。无明确数值限值/方法/单位不自动判合格。机台设定温度不填实测模温；两种硬度不互相复制。
- 整模完成必须有整包范围、明确完成确认、实际作业人及业务时间。部分/未知范围不能仅勾完成。定点按每条实际范围解释，不取末值/最大/平均冒充整包一致；异常处理须另有实际处理及已解决确认。
- `400总孔/396有效孔（已含4定点）`再登记4，仍是396。登记6只留下新范围及待核对依据，不改主数据、卡计划、日志、库存或交付。
- 补打保留原卡号、日期、要求、模板和关联；0次不显示。下载不改次数；每卡仅一项活跃打印预约。结果未知继续原任务，用户确认部分成功范围，不把预览关闭当出纸证明。
- 每个打印任务PDF冻结于私有目录并存SHA256；GET只读原件，不重新渲染。缺原文件报错，不用当前模板冒充原件。老渲染器不可用时拒绝套新模板。
- 出货确认和来源绑定同事务；来源错误整笔确认回滚。无新来源时旧确认合同不变。
- 出货明细重建后，来源仍挂稳定Batch，原快照不丢；状态转待核对。人工重新核对创建新版本并将原关系标“已替代”，撤销标“已撤销”，都留原证据，不改数量。
- 身份明确冲突拒绝绑定；身份缺项可保留待核对，不变成虚构冲突或自动确认。
- 没有精确份额时只说涉及集合。同卡多次来源关联不证明每次整包消耗，不提供伪造的“包余额”。独立物理拆包子卡未实现，不允许拿补打当拆包。

新增模型都在`backend/flowcards/models.py`：`AppearanceIssue`、`StandardRevision`、`PositionDiagram`、`CardGroup`、`InternalCard`、`PrintJob/PrintItem`、`TemplatePublication`、`CardEvent`、`Attachment`、`ShipmentSource`、`TraceAudit`。旧模型无新增数量字段或回填操作。

## 5. 可追溯隔离案例与数量核对

以下全部为合成隔离样本，**不是215/N7200正式账实测**。测试断言可从`backend/flowcards/tests.py`同名用例重跑。

### C1：跨订单、多个来源与再次使用同来源

`test_A15_A16_many_sources_cross_order_and_reuse_do_not_multiply_delivery`：同客户同产品订单甲需求50、乙80，一次物理出货100，原服务分配甲50+乙50；关联两张内部卡后总交付仍100。第二次100件再次关联原卡“部分使用、份额未知”，两次总有效交付200，不是按来源卡数量翻倍。原服务允许的超交仍由原算法处理，新卡不改去向。

### C2：同批两轮退回再发

`test_A18_two_return_rounds_keep_original_sources_and_no_fake_rework`：100件首发→全退→再发→全退→再发，净有效交付仍100。来源保原Batch，能查两轮案件和再发ID；实际返工作业条数保持0，**0条系统记录不等于现场未返工**。没有因为再发创建假返工作业。

105条退回历史另用`test_A18_long_return_history_is_paginated_not_truncated`验证：首屏20，6页末页5条，数量105，不再静默截断100。此105条只是分页压力样本，不代表105轮合法实物退回。

### C3：手工库存出库与客户出货边界

`test_A22_manual_stock_out_and_customer_shipment_are_separate_no_double_deduction`：待检库存200，人工出库100后容器100、订单交付0；随后原品检出货100并关联内部卡，订单交付100，容器仍100、无第二条扣库流水、原库存仍待检。说明两个账独立，不是已实现逐件库存来源关联。

### C4：缺记录、准备及原图

无计划模数只能准备，生产任务/日志数不变；补齐80模后同组生成一张80M卡，生成后拒绝改原快照。只上传照片时仍是“需整模·系统未登记”；没有照片不能恢复未知手写值。来源客户旧快照未知、当前出货客户后来确认时，保留“待核对”而非自动认领。

### C5：不可变标准与更正

原检验上限180改为190、词库改名后，旧卡仍保留180及旧问题名称；旧打印任务GET的PDF字节不变。重量更正将出货明细重建、净交付从100变90，来源卡仍挂原Batch并待核对；人工复核另建集合关系，旧快照不改。

### 旧表摘要

`scripts/flowcards_acceptance.py`只接受全新`.codex_tmp/*.sqlite3`。先迁移旧应用，建立合成产品/两个订单/396孔任务/100模日志；记录旧业务表逐行SHA和行数，再迁移新应用，再生成120张卡及100条范围记录。

最终`evidence.json`记录：迁移前后旧表摘要一致；制卡/记录前后旧表摘要一致；1/100卡绑定前后各自旧表摘要一致。注意：部分旧表在合成样本中为空，**不能据此替代真实生产副本全账回归**。本轮无猜填历史、无整库导出。
