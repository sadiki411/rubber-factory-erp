# 原筐/袋追加入库（2026-11-09）

## 确认的业务范围

用户提出：原筐未装满，需要在原有库存基础上继续放同一产品，增加数量。
本次用户明确确认：

- 只向同产品、同检验状态的原筐/袋追加；合格与待检不能混放。
- 本次增加部分单独登记入库日期和品检员，允许不同于原批次，不自动沿用或归到原品检员。

这不是直接修改库存总数，也不是盘盈、旧账更正或替原记录重算。

## 使用入口与数量口径

成品库存的库位表、库位详情中增加“追加入库”。手机扫描库位后打开的现有详情也使用同一入口。
输入“本次增加数量（件）”，界面同时显示“原有 + 本次 = 追加后”。
需要确认本次检验状态与原筐一致；已检合格货必须选择本次品检员。日期默认今天，可改成本次真实入库日期；检验日期、备注、追加后袋数可选填。
袋数是追加后的绝对袋数，不填保留原值；件数不由袋数乘每袋数反推，每袋数量不自动更改。

例：原有4,000件，追加500件，权威容器余额为4,500件；随后人工出库1,000件，余额为3,500件。重试第一次500件追加的原提交，只返回原成功回执和当前3,500件，不再增加500件。

## 数据关系和边界

- 权威余额仍为 `InventoryContainer.quantity`，汇总/可用量仍按现有容器余额计算。
- 不新建另一只容器、另一个库位或另一份余额；原库存批次号、筐编号、首次入库日期及批次品检员保持原值。
- 每次新增一条入库流水，流水数量仅为增加量。
- 新表 `InventoryTopUp` 与这条流水一对一，保存本次日期、品检员ID和姓名快照、检验日期、质量状态、产品身份快照、追加前后件数/袋数及请求防重标识。
- 库位详情的“追加入库记录”按需分页读取，每页30条；加载中、失败和真实空记录分别显示。列表不会对每个库位逐一发历史请求。
- 原批次品检员不代表所有后续增加部分的品检员，界面明确区分。原品检员字段可能被现有“改质量状态”功能更正，不能宣称它是不可变的首次检验事实。
- 追加记录保留当时的品检员/产品快照，后续改名不改写本次快照。匿名微信库位历史只显示追加操作、产品身份、库位与数量，不暴露人员、备注或请求标识。
- 人工库存出库与品检流程卡出货的独立关系不变；追加不会生成品检出货单，也不改变订单交付数量。
- 同一筐混放后，本次记录可证明每笔入库事实，但不能证明后来任意出库的每一件分别来自哪次追加。本轮未引入分层余额/FIFO、逐次追加品检绩效或旧记录补造。

## 防错与权限

提交携带打开窗口时的产品身份、库位、数量及记录版本。期间发生出库、移库或产品/质量变化，会拦截并要求关闭刷新核对，不静默覆盖。
只有在用、有正余额、有库位且产品/库位启用的筐袋允许追加；空筐或已关闭容器走原直接入库。
负数、0、小数、缺日期、合格货缺本次品检员、停用品检员、超过整数上界均不入账。

服务端在同一事务中更新余额并保存入库流水/本次事实；任何一步失败，全部回滚。
每次提交使用持久化唯一请求编号和内容摘要。同编号同内容同用户同容器只生效一次；改变内容或挪用编号返回冲突。网络错误后窗口保留原内容和编号用于重试；发生冲突必须先核对库存，不允许盲重试。
SQLite行锁有限，使用版本条件更新和整笔事务的有界锁冲突重试；不在旧快照内盲重试。两笔不同请求同时基于同一旧余额确认，只允许一笔成功，另一笔需刷新核对。
既有只读账号可看历史，不能追加入库；匿名只能使用现有公开只读库位接口。
