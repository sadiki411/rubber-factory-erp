# 库存待检状态修复与验收

## 根因

1. 库存明细表最右侧已有改质量状态和移库入口，但库位详情没有入口；手机横向表格难以发现操作。
2. 质量状态表单不分状态，全部强制要求品检员和检验日期，导致待检、冻结等更正也被阻止。
3. 库位详情保存点击时的旧对象，查询刷新后仍可能展示旧状态；库位接口没有返回已登记品检员ID和检验日期，打开表单又清空员工。
4. 状态接口对非法参数和空容器保护不足；无变化保存也反复增加状态流水。

## 修复与规则

- 点击成品库位后直接提供“更新质量状态”“移库”“更正产品资料”；已检合格时提供预选当前容器的“办理出库”。手机按钮允许换行，触控高度不低于44px。
- 待检、不合格、冻结库存可以移库或更正状态，但不能绕过实际品检正常出库。改为已检合格必须选择有效品检员，日期可选；已记录的员工和日期自动带回。
- 状态更新不改变库存数量和库位；有效变化保留前后状态、员工ID和日期流水，相同参数重试不重复记流水。空容器不能用来改写批次质量记录。
- 库位详情绑定最新查询结果，避免保存成功后仍展示旧状态。
- 容器编号搜索同步作用于货架图和可操作表格。库位读取失败显示重试，不误显示初始化入口。
- 非法日期、员工、移库目标、出库引用、重复容器行和重复指定出库单号返回明确校验错误。多行出库失败必须整单回滚。
- 库存页面各表单校验不通过时就地保留输入和字段提示，不再抛出未处理的异步异常；补测空入库/出库表单和漏选品检员。
- 库存仍独立于订单和流程卡，库存出库不会自动制造品检出货事实。固定库位和历史数量不变；无数据库结构迁移。

- `makemigrations --check --dry-run` 无模型变化；前端ESLint、TypeScript、生产构建通过。
- 前端库存专项14/14通过，进程退出码0；覆盖详情入口、待检转冻结无需员工/日期、合格必须员工、合格后出库并释放库位、原品检资料带回、保存失败保留表单、容器搜索、读取失败重试和入库/出库漏填校验。其余前端全套结果见发版记录。

## 后续库存更新必须回归的场景

1. 待检入库后，从桌面和手机库位详情均能移库、更新状态；待检不能正常出库。
2. 待检/冻结/不合格可互相更正，不强制补造品检人员和日期；改合格必须实际登记员工。
3. 合格后部分/全量出库；全量出库释放库位且原位置可再次入库；不能超扣、重复扣减或失败后部分扣减。
4. 状态更正不改数量和位置；历史品检资料能带回；空容器不能改写质量历史；刷新后的详情与接口一致。
5. 错误参数、保存失败、读取失败和相同参数重试；错误后保留输入且显示真实结果。
6. 至少360/390像素手机和桌面布局；单测随常规CI运行，不能只验证后端“禁止待检出库”而遗漏后续转状态路径。
