# 出货卡身份追溯：实现边界与验收

## 正式范围

本轮仅增强读路径：出货详情展示明确卡证据；每日出货及重量批次按卡反查；流程卡增加“出货追溯（全部历史）”。不迁移模型、不更正正式数据、不改变分摊算法、不自动扣库存。

卡的原始纸卡订单、当前系统来源订单、实际订单交付分摊是三种不同事实。系统来源可能由历史自动选单生成，不能独立认证纸卡原始订单。未核验的原始凭据保持未知。

## 关系与数量

`quality/tracing.py` 复用明细直接外键、独立包绑定、退回来源/再发、同 tracking_id 换卡链、更正前后快照。只解析结构化身份字段，不搜备注、不按规格或号码段猜配。

- 一个QS只记一次出货事件；整单量和本卡已保存包量分开。
- 包绑定再发时可能移动；原首发通过退回来源继续可查。退回件数可能是部分退回，不能作为原包量补回。
- 更正快照保留历史身份，但旧快照的包量不能冒充当前更正后的包量。
- 无保存件数但有历史单重时，沿用既有折算函数并标注折算；无依据则返回null，不造0。
- 列表仍遵守日期/状态筛选；全部历史入口不受列表日期限制。
- 卡号至少4字符参与卡身份查询，多个候选只查询、不绑定。
- 批量来源附加的查询次数不随批次数逐行增长。修订快照查找目前扫描已有修订JSON，历史大幅增长时仍须测量；不宣称无限数据规模已达标。

## 隔离分摊原型

`quality/prototypes/allocation_review.py` 无URL、无模型写入，不被生产服务导入；容器构建不包含该子目录。复用现有planner，演示预览指纹、余额变化要求复核、原请求重试返回同一内存回执。

内存回执不是持久化幂等机制，不证明跨进程并发安全；正式落地需要事务内余额/版本校验、持久化请求唯一性及响应重放。未获确认前不能接正式确认接口。

## 更正能力核对

现有`amend`需要原因、保存前后快照、时间与操作者；失败会事务回滚。已登记返工实际作业不按原出货重量同比改写；删除会孤立实际作业的包会阻止。已有下游关联的整单作废受保护。

独立包绑定更正且交付事实不变的样本，可以保持已保存分摊。直接明细卡、来源订单或数量改变可能触发重放分摊，不能据此承诺“所有更正都只改显示”。尚无独立的通用“仅补来源证据且预览全链影响”确认流程；P1-D本轮只提供核对及后续方案，不补改真实历史。

## 测试位置

- `test_shipment_tracing.py`：七卡反查去重；首发无退回；两轮退回再发＋换卡；修订身份查找；缺值；只读无写；批量查询数；仅独立绑定更正不改交付和库存。
- `test_allocation_review_prototype.py`：65,933及9,597件的隔离分摊；确定性交错模拟余额变化；模拟丢响应重试。不冒充真实并行HTTP或弱网测试。
- `test_confirmed_shipment_corrections.py`：既有更正、失败回滚、实际返工值保护、历史分摊保护、下游作废保护。
- 前端`QualityShipmentTrace.test.tsx`及现有品检组件/页面测试：卡折叠、加载/错误/重试、无退回首发、缺值不造0。

手机实机排版、相机扫码、剪贴板权限、弱网、正式并发和公网2秒体验需要现场验收；本地DOM测试不等于这些已通过。专项真实数据证据与本机审阅原型保存在交付目录，不提交公开仓库。
