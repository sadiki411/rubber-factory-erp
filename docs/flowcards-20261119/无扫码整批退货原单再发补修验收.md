# 无扫码整批退货后沿原退货单再次出货：隔离验收

日期：2026-11-19。原分支：`codex/flow-cards-20261118`。本轮基础提交：`86b2698092eaa7c83904eb9973277d3ead14bee3`。

## 结论与边界

本轮仅补用户指定的“无扫码整批退货后，沿原退货单再次出货”。两个退货入口均已用全新合成数据，从普通员工页面完成净交付 **100→0→100**。

- 原出货的该实物包只有一张有效客户流程卡时沿用；多张、缺卡、串到其他包/出货轮次时提示人工核对，不按规格、日期或订单猜配。
- 再发沿原退货单生成关联的再发出货记录，不另开首次出货；不新增退货、不重建回冲。
- 原出货责任品检员不变。本轮再发品检员必须在页面重新选择，不自动继承原责任人。
- **未推送、未部署、无数据库迁移、未访问或改写正式账。**上轮工序卡事项和其他业务均暂缓。隔离库的工序卡正式写入开关关闭。

“已完成”的范围是本地补修、隔离验证及证据交付；不是已上线、不是安卓实机验收通过。

## 1. 根因

无扫码整批退货原本已经按原出货和物理批号生成退货单及逐订单回冲，但该退货单可能没有直接的客户流程卡关联，状态也未必是旧再发服务要求的 `WAITING_REWORK`。旧详情页没有“沿原退货单再发”的直接操作。

因此问题不是应再建一笔首次出货，也不是再退一次货；缺的是“核实原实物包唯一客户卡→复用原退货单进入既有再发链”的连接。

依据：`backend/quality/services.py` 的原 `reship_return_case`、整批退货分摊及 `ProcessCardUnitBinding`；`frontend/src/components/QualityReturnReworkDrawer.tsx` 的原详情操作。代码证明本轮检查到的行为，不代表推断所有历史失败记录的原因。本轮没有扫描正式历史或补造旧关联。

## 2. 最小修改

### 后端

新增只读 `GET /api/quality/rework-cases/{id}/reship-context/`，由 `return_reship_context` 核对：

1. 客户整批退货、原已确认出货、明确物理批号、待处理状态。
2. 证据仅取原出货该实物包的绑定、实际出货行直接流程卡、该退货单已有流程卡。
3. 已有补卡换号按审计替换链归到当前有效卡；取消卡排除。
4. 唯一有效卡仍须属于此原实物包，且无另一笔待处理退货；否则停止并提示核对。
5. **GET 不修改任何历史。**唯一关联的补齐只发生在用户明确提交原单再发的事务中。

修改既有 `POST /api/quality/rework-cases/{id}/reship/`：

- 事务内再次锁定并核对，不信任页面先前读取的结果。
- 唯一明确的原直接出货行卡缺当前绑定时，恢复这一确定关联；不借其他实物包的卡。
- 复用原退货分摊和旧再发服务。补齐关联/轮次不调用退货服务、不新建 `QualityReturnAllocation`。
- 同原退货单、同日期/重量/数量/品检员的重复提交返回原再发记录；不同事实拒绝重复建立。
- SQLite锁冲突沿既有完整事务重试机制处理；失败整体回滚。

本轮未改变原再发允许修改重量/件数及按原分摊比例分配的既有规则。100件样本恰为60/40，不涉及额外舍入。

### 前端

原位置：**品检出货 → 退货返工 → 原退货记录“查看” → “沿本退货单再次出货”**。

- 直接在原详情内填写本轮日期、重量、数量和本轮品检员，不跳到首次出货页。
- 多卡/无卡显示“需要人工核对，暂不出货”，没有确认再发按钮；读取失败单独显示错误及重试，不当作缺卡。
- 成功响应立即显示原退货单“已重新出货”和关联再发记录；后续列表刷新失败不误报保存失败。
- 同一时间线立即使用本次成功响应，避免仍显示旧“待返工”。

人工核对后的通用历史补关联界面不在本轮新建范围；不确定记录保持阻止，不提供猜配兜底。

| 无扫码入口 | 498d501ebc2f63b39c55c97c2e6331711894eb02af2b19c6972868d40e1a40ca |
